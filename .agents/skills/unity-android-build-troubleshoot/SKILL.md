# Android CLI build troubleshooting

## Diagnostic order

1. **Check the log before touching any code.** A CLI Android build writes its full output to `-logFile <path>` (see the `unity-cli-batchmode` skill for the general batchmode logging/exit-code caveats — the same "don't trust the exit code alone" rule applies to builds, not just tests). Search the log tail for the actual Gradle/SDK error string rather than guessing from the wrapper script's own exception message — `BuildAutomation.BuildAndroidDevelopment` (this repo's `Assets/Editor/BuildAutomation.cs`) throws a generic `BuildFailedException` with only `report.summary.result`, which tells you *that* it failed, not *why*.
2. **Confirm Unity actually finished before checking for output.** A CLI wrapper that inspects the exit code or checks for the output APK immediately after launching Unity is only correct if it genuinely waited for the batchmode process to exit. On Windows, `Unity.exe` is a GUI-subsystem executable; PowerShell scripts in this repo learned this the hard way once already — `scripts/Run-UnityTests.ps1` explicitly switched to `Start-Process -FilePath $UnityPath -ArgumentList $arguments -Wait -PassThru` after finding direct invocation unreliable for blocking until batchmode completes (see its own inline comment). **`scripts/Build-Android.ps1` still invokes Unity via plain `& $UnityPath ...` rather than `Start-Process -Wait`** — if a build ever appears to fail or "succeed" implausibly fast, or `$LASTEXITCODE`/the APK-existence check look wrong, this inconsistency between the two sibling scripts is the first thing to rule out, not the Android toolchain itself.
3. Only after 1–2 point to something Android-specific, work through the causes below.

## Toolchain resolution (SDK / NDK / JDK)

This project's Android Build Support was installed via Unity Hub as a module (per `CLAUDE.md`), which bundles a matching SDK, NDK, and OpenJDK and has Unity auto-detect them — no manual path configuration should be needed in the common case. Symptoms and fixes if toolchain resolution breaks anyway:

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `Android SDK not found` / `Unable to locate Android NDK` | Unity's External Tools preferences point at a missing/stale path (e.g. after moving the Hub install, or a partial module install) | Editor > Preferences > External Tools: verify SDK/NDK/JDK all resolve. Prefer "Installed with Unity" over a hand-picked external path unless there's a specific reason to pin one. |
| `JAVA_HOME is set to an invalid directory` | A machine-level `JAVA_HOME` environment variable overrides Unity's bundled JDK and points somewhere Gradle can't use | Unset `JAVA_HOME` for the build environment, or point it at a JDK version Unity's bundled Gradle actually supports (check External Tools for the version Unity expects). |
| `Failed to install the following Android SDK packages as some licences have not been accepted` | A referenced SDK platform/build-tools version's license was never accepted (common on a fresh machine/CI runner) | Open the SDK Manager once interactively (via Preferences > External Tools > SDK path > run `sdkmanager --licenses`, or open the Editor normally once) — this is typically not resolvable purely from an unattended CLI run the first time. |

## Signing / keystore

`BuildOptions.Development` (what this repo's `BuildAutomation.BuildAndroidDevelopment` passes) uses Unity's auto-generated debug keystore — no manual keystore setup is needed for this prototype's development-build scope, and GAME.md's out-of-scope list doesn't call for release signing yet. Keystore/signing errors (`Keystore file not set for signing config release`, `Invalid keystore format`, mixed `/`/`\` path separators on Windows) only become relevant once Player Settings > Publishing Settings gets a real keystore for a release build — don't pre-configure signing before the project actually needs a release build.

## Scripting backend: IL2CPP is not optional for a real device install — and this project has not set it

Mono cannot produce an `arm64` binary — there is no configuration in which a Mono-backend Android build installs on an arm64-only device, which is effectively every current Android phone (Google Play has required 64-bit native libraries since 2019, and 32-bit-only silicon is functionally extinct in phones sold new). Practically: **`Player Settings > Configuration > Scripting Backend` must be IL2CPP** for this project's "installs on a real device" acceptance criterion (GAME.md's "An Android development build installs and reaches the Terrarium screen") to be achievable at all — Mono's only remaining legitimate use is Editor Play Mode and fast local iteration, not a device build. If a development build ever needs to be *fast to iterate on* rather than device-installed, that's a reason to test in the Editor via Play Mode, not a reason to switch the Android target to Mono.

**Unity's own manual states it plainly: "When a platform can support both backends, Mono is the default."** Android is one of those platforms (unlike iOS/WebGL, which have no Mono option and are forced to IL2CPP), so Android's default is Mono, not IL2CPP. Checked directly in this repo: `ProjectSettings/ProjectSettings.asset` has `scriptingBackend: {}` — an empty map, meaning no per-platform override has ever been set, so this project is currently on Unity's Android default, **Mono**, and an Android build attempted as-is would very likely produce an APK that cannot be installed on a real device. This must be set to IL2CPP (via `Player Settings > Configuration > Scripting Backend`, or `PlayerSettings.SetScriptingBackend(BuildTargetGroup.Android, ScriptingImplementation.IL2CPP)` in an idempotent Editor bootstrap step, the same idempotent-setup pattern as `ProjectBootstrap.cs`) before the Android build task is attempted for real — treat this as the first thing to check/fix, before any of the Gradle/SDK troubleshooting below, since an installed-but-wrong-backend build fails in a way that looks like a device/Play-Store problem rather than a project-configuration one.

Trade-off to expect, not to treat as a bug: IL2CPP compiles ahead-of-time (C# → IL → generated C++ → native code via the NDK's C++ toolchain), which is measurably slower to build than Mono's JIT approach — budget more CLI wall-clock time for an Android build than for the EditMode/PlayMode test runs this project's scripts already automate, especially the first build after a Library cache clear (IL2CPP's generated-C++ compile step is the dominant cost, and it is not fully incremental the way C# compilation is).

## Gradle / Android Gradle Plugin (AGP) version — check, don't assume

The Gradle and AGP versions Unity actually bundles change across `6000.x` point releases. Unity's own "Gradle version compatibility" page lists which Gradle/AGP pairs are *compatible* with which Editor version (for 6000.2, that table lists Gradle 8.13 / AGP 8.10.0) — note that this is a compatibility table, not an explicit "ships with" statement, so treat it as "known-good pairing" rather than "guaranteed bundled default." Unity's own upgrade-guide material separately references a later jump to Gradle 9.1.0 / AGP 9.0.0 for a subsequent `6000.x` release. Either way, do not hardcode an assumed version pair anywhere (a custom Gradle template, a CI config, documentation). If a build fails with a Gradle/AGP-version-shaped error, confirm the actual bundled versions for the exact installed Editor (`6000.5.3f1` for this project) via `Editor > Preferences > External Tools`, or by reading the generated `gradle-wrapper.properties`/`build.gradle` in the CLI build's temporary Gradle project output, rather than trusting a remembered number from a different point release. If this project ever enables a **custom Gradle template** (`Player Settings > Publishing Settings` — not currently enabled), any hand-maintained `.gradle` file becomes responsible for staying compatible with whatever AGP version that Editor version ships, and Unity's own upgrade guides call out reviewing custom templates for deprecated attributes after an Editor upgrade as a manual step, not something the upgrade does for you.

## Before the first real device test: sanity-check touch target sizes

This project's UI is authored in USS `px` values against a `PanelSettings` reference resolution of 1080×1920 (`ScaleWithScreenSize`, `MatchWidthOrHeight`, `match: 0.5`) — those pixel values are reference-space, not physical device pixels, and how large they end up *feeling* on a real finger depends on the actual device's physical density, which isn't knowable from the Editor alone. Google's Material Design guidance recommends a 48dp minimum touch target; Apple's HIG recommends 44pt. This project's own USS has a real spread worth a first-real-device glance rather than assuming reference-`px` sizing is automatically fine: care buttons and decor-drawer rows are `56px` tall (comfortably above typical guidance), the debug panel's `1x`/`60x`/`600x` multiplier buttons are `40px`, and the corner debug toggle is the smallest interactive element in the whole UI at `32px`×`64px`. The debug panel is dev-only (a developer's own thumb, not an average player's), so this isn't launch-blocking, but it's the first thing to actually tap on a physical phone once a build installs — if the smallest buttons feel cramped, that's the one to enlarge first, not a sign of a deeper problem.

(One historical UI Toolkit touch-input bug worth knowing does NOT apply here: a Unity Discussions thread describes touch coordinates becoming offset from visuals when the screen ratio differs from the reference ratio, but that was a confirmed bug from the `2021.2`-era UI Toolkit preview package (Case 1288368), fixed years before this project's `6000.5.3f1` — checked and ruled out, not a live concern for this Editor version.)

## `BuildFailedException` from this repo's own guard clauses

Before any Android/Gradle concern, rule out the two explicit guards already in `BuildAutomation.cs`: "No scenes are configured in Editor Build Settings" and "No enabled scenes are configured" — both mean `EditorBuildSettings.scenes` is empty or every entry is disabled, which is a project-configuration issue (see the `unity-project-scaffold` skill's bootstrap pattern for how the scene list gets wired), not an SDK/Gradle problem.
