### トピック2: 「ケージの半分以上が見えない」問題の定量検証

**LP1（情報収集）**:
- Unity Discussions/Forumで "ScrollView not scrolling if initial touch is a button" 等を検索。ヒットした主要スレッドは旧uGUI（ScrollRect + EventTrigger）の話で、本プロジェクトが使うUI Toolkit（UIElements）の `ScrollView` + `Button`（`Clickable`マニピュレータ経由でコンストラクタにコールバックを渡す実装）には直接当てはまらない。
- UI Toolkit公式ScrollViewの既知バグ報告（elasticity/velocity/frame-rate関連）を確認したが、「Buttonで覆われているとスクロールできない」という報告は見つからなかった。
- 本プロジェクト内で同じ「ScrollView + 全面Buttonの行」パターンは `CageListView`（ケージタブ）、`ShopView`、`LedgerView`、`PairingView` でも使われている。これらのスクロールが壊れているという報告は今まで出ていない → 同じ実装パターンが他画面では機能している傍証。

**LP2（比較・現状分析）**:
- `Assets/UI/TerrariumPanelSettings.asset`: `m_ScaleMode: 2`（Scale With Screen Size）, 参照解像度 390×844, m_Match: 0.5。iPhone 15 Pro（1179×2556物理px / 3倍率 = 393×852 論理pt）で計算すると、パネルのスケール係数は約3.02〜3.03倍 ≒ 実機の1pt。つまりUSSの `px` 単位は実機上でほぼ1:1で論理ポイントに対応する（この機種では）。
- 実機の safe area（iPhone 15 Pro縦向き目安）: 上部ノッチ/Dynamic Island 約59pt、下部ホームインジケータ約34pt。`scripts/capture-screens.sh` のレンダーキャプチャはこのsafe areaを再現しない（SKILL.mdに明記済みの既知の限界）→ これが今まで気付けなかった一因。

**検証（影響範囲を具体的に算出）**:

実機縦画面の高さ配分（pt ≒ USS px）:
```
画面高さ                          852
- safe area 上(ノッチ)            -59
- safe area 下(ホームバー)         -34
= 実質使用可能高さ                  759

固定UI（ホーム画面）:
  app-header                       40
  environment-bar                  24
  screen-title（22px+margin16px）  ~42
  home-incubator-button（48+margin20） 68
  tab-bar（画面下部・常時表示）      56
  固定UI合計                       230

rack-list（ScrollView）実質高さ = 759 - 230 = 529px
```

1ラックの行の高さ:
```
phase4後: rack-slot 120 + row padding16 + border-bottom6 + margin-bottom12 = 154px/行
phase4前: rack-slot 110 + row padding16 + border-bottom6 + margin-bottom12 = 144px/行
```

スクロールなしで見える行数:
```
phase4後: floor(529/154) = 3行(462px) + 4行目が67px(43%)だけ覗く
phase4前: floor(529/144) = 3行(432px) + 4行目が97px(67%)だけ覗く
```

**結論（確度: 中〜高、実機未確認のため断定はしない）**:
1. phase4前後どちらでも、スクロールなしで完全に見えるのは **最大3ラック（12ケージ）分だけ**。4ラック目以降は常にスクロールが必要 — これはphase4だけの問題ではなく、以前から存在した潜在的な制約。
2. phase4の変更（rack-slot 110→120px, rack-alert 16→26px）による行の高さ増加は 144→154px（+10px/行）で、4行目の「覗き」が67%→43%に減っただけ。「今回のUI増加で急に半分以上見えなくなった」というより、**ラック数が増えるほど元々スクロールが必須だった設計に、プレイヤーの手持ちラック数が達した**可能性が高い。
3. `.rack-list` にスクロールバーのカスタムスタイルは無し（Unity既定のスクロールバーのまま）→ 地味で気づきにくい可能性はあるが、4行目が最大43%覗く設計自体は「まだ続きがある」というヒントとしては機能しているはず。
4. 同一実装パターン（ScrollView+全面Button行）が他画面（ケージ一覧・ショップ・台帳）で問題なく使われている実績から、**スクロール機能自体が壊れている可能性は低い**と判断する。

**修正**: 今回は適用しない。理由 — これは「壊れているバグ」ではなく「何ラックまで一目で見えるか」という見た目の設計判断であり、GAME.mdにも密度の仕様は無い。密度を変える（rack-slotを小さくする等）のはプレイヤー体験に直結する意匠判断であり、実機確認なしに自律モードで変更すべきではない（[[phase-workflow-regime]] の「プレイヤーに見えるものはユーザー判断」の原則）。

**ユーザーへの提案（朝の判断用）**: 次のいずれかを教えてもらえれば確定できる。
- (a) 実機のホーム画面のスクリーンショット、または
- (b) ケージグリッドを上に向かってスワイプしたときに実際にスクロールするかどうか（する/しない）

候補の対応案（優先度順、どれもリバーシブル・低リスク）:
1. **何もしない**: 3ラックまでは全て見え、4ラック目以降は覗き＋スクロールで到達可能。仕様として許容するならこれが最小変更。
2. **密度を上げる**: `.rack-slot` の height を 120→100px程度に戻す/縮める、`.rack-row` の margin-bottom を12→8pxに縮める等で1画面に収まる行数を増やす（タップ領域は多少狭くなる）。

### トピック3: フェーズ3/4の脆弱性・保護観点レビュー（経済・セーブデータ・ショップ）

**LP1（情報収集）**: 「シングルプレイヤーのモバイルゲームにおけるローカルセーブの改ざん対策」についてWeb検索。業界一般の知見:
- セーブ改ざんの典型手口は「JSONを直接編集して所持金を書き換える」等（[GuardingPearSoftware](https://www.guardingpearsoftware.com/knowledge/runtime/save-game-tampering)）。
- 対策の主流はチェックサム/HMAC検証、値の暗号化・難読化、メモリ改ざん対策、そして「オンライン対戦・課金・ランキングが絡む場合はサーバー側検証が唯一の確実な方法」という整理（[Promon](https://promon.io/security-news/prevent-cheating-in-gaming-apps), [Bugnet](https://bugnet.io/blog/how-to-fix-tampered-save-files-cheating)）。
- 裏を返すと、オンライン要素・課金連動が無い純粋オフラインのシングルプレイヤーゲームでは、セーブ改ざんは「自分だけが得する自己満足チート」に分類され、業界でも対策を省略する作品が多い（牧場経営・ペット育成・放置ゲーム等の同ジャンルに広く見られる傾向）。

**LP2（比較・現状分析）**: 本プロジェクトのセーブ/経済/ショップ実装をコードから直接確認。
- 保存先は `Application.persistentDataPath`（[TerrariumView.cs:342](Assets/Scripts/UI/TerrariumView.cs:342)）— OS標準のアプリ専有サンドボックス。他アプリからは読めない、業界標準的な配置。
- 保存形式は平文JSON（`JsonUtility`）で、チェックサム・署名・暗号化は無し（[ColonySaveService.cs:124](Assets/Scripts/Core/ColonySaveService.cs:124)）。
- ロード時、所持金・ジーン型・インベントリ数量などは検証なしにそのままクライアント側の値として信頼される（例: `colony.Wallet.Money = data.money;` [ColonySaveService.cs:212](Assets/Scripts/Core/ColonySaveService.cs:212)）。理論上、ファイルを直接書き換えれば所持金や遺伝子型を自由に変更できる。
- IAP/課金コードの有無を全文検索 → **0件**（`IAP`/`StoreKit`/`billing`/`receipt`等でヒットなし）。オンライン通信・ランキング・マルチプレイヤー要素も無し。つまり改ざんの影響は**本人のシングルプレイヤー体験のみ**に閉じ、他プレイヤーへの実害・運営側の金銭損失・ランキング不正は発生し得ない構成。
- 一方、「悪意ではない破損」への堅牢性はすでに良好に実装済み: JSON形式の事前検証→失敗時は例外化してキャッチ、壊れたセーブは`.corrupt-*.bak`にコピーしてから新規作成（[ColonySaveService.cs:58-106](Assets/Scripts/Core/ColonySaveService.cs:58)）、書き込みは`.tmp`+`File.Replace`でアトミック（同108-133行）、enum値は`TryParseDefined`で未定義値を安全にデフォルトへフォールバック（既存コメントで「数値インデックスの範囲外アクセス防止」と明記済み、653-693行）、未知の装飾品idも`DecorItems.LabelOf`はid文字列をそのまま返しクラッシュしない（[DecorSlots.cs:32-43](Assets/Scripts/Core/DecorSlots.cs:32)）、UIの装飾アイコンもUSSクラス名ベース（`decor-icon-{id}`）で未知idでも例外を出さない（[TerrariumView.cs:1542](Assets/Scripts/UI/TerrariumView.cs:1542)）。

**検証（影響範囲・メリデメ・リスク）**:
- 影響範囲: 改ざんが可能な項目は「自分のセーブファイル」に限定。同一ファイルを他人と共有・比較する仕組み（クラウド同点ランキング等）は存在しないため、被害者が生まれない。
- 対策（チェックサム/HMAC/暗号化）を追加した場合のメリット: カジュアルな改ざんの心理的ハードルをやや上げられる。
- デメリット/リスク: (1) 実装・テストコストが発生、(2) 既存セーブとの後方互換のためのマイグレーション設計が必要、(3) クライアント埋め込み鍵は原理的に解析されうるため「気休め」以上の効果は薄い、(4) デバッグ・サポート時のセーブ内容の目視確認がしづらくなる。
- 費用対効果: 実害シナリオが存在しない現状の構成では、投資対効果が低いと判断。
- 逆に、既存の「破損データへの堅牢性」は前述の通りすでに十分な防御層があり、追加の緊急対応は不要。

**修正**: 今回は適用しない。理由 — (1) 実害（他者への影響・運営コスト・課金詐取・ランキング不正）が生じない構成であることをコード上で確認済み、(2) 改ざん対策の要否・強度はゲームの将来スコープ（オンライン要素や実績共有の追加予定の有無）に依存する設計判断であり、GAME.mdにも記載が無い → ユーザー確認事項とする。

**ユーザーへの提案（朝の判断用）**: 現状は対応不要と判断していますが、以下のいずれかの予定がある場合はチェックサム/サーバー検証の導入を検討する価値があります。
1. 将来オンラインランキング・フレンド間比較・実績共有機能を追加する予定がある
2. 将来ゲーム内通貨と連動する課金（ブースター購入等）を追加する予定がある
3. 上記いずれも無ければ、現状の「セーブは平文・改ざんは自己責任」のままで問題なし（同ジャンルの一般的な扱いと一致）

### トピック4: 類似ブリーダー/ペット育成ゲームのUI/UXパターン比較調査

**LP1（情報収集）**: Web検索で3系統の実例を確認。

- **Flight Rising（ドラゴン飼育のWebゲーム）の「Lair」**: プレイヤーはタブ＋ページでコレクションを自由に整理でき、新規個体は自動的に「ドラゴンInbox」＝最終ページに送られ、紫の矢印アイコンで新着であることが明示される。さらに「Hibernal Den」という、アクティブ上限を消費しない“観賞用の退避収納”を別途用意している（[Flight Rising Wiki](https://flightrising.fandom.com/wiki/Lair_and_Lair_Space), [公式アナウンス](https://www1.flightrising.com/forums/ann/2627065)）。
- **一般的なUI設計論**: ページネーションは「情報量の圧倒を防ぐ」「表示件数を絞ることでパフォーマンスを保つ」「スクリーンリーダー等アクセシビリティに有利」という利点がある一方、連続スクロール（無限スクロール/遅延読み込み）はページの概念がなく、フィード的なコンテンツに向く、という整理が一般的（[Setproduct Blog](https://www.setproduct.com/blog/pagination-ui-design)）。

- 新規に増えたラック/ケージを視覚的にハイライトする仕組みが無い（Flight Rising方式との差 — 新着個体を紫矢印で明示する発想は本作には無い）。
- 「アクティブ上限を消費しない退避収納」に相当する概念も無い（Hibernal Den方式との差 — 本作は購入したラック・ケージはすべて常時「アクティブ」として同じリストに並ぶ）。

**検証（影響範囲・メリデメ・リスク）**: これは意匠・情報設計の選択肢を広げる調査であり、いずれも実装すれば相応のコストと互換性検討（既存セーブのラック順序・UIレイアウト変更）を要する設計判断。トピック2（サイクル1）で保留した「スクロール発見性」の課題に対し、以下を追加の選択肢として提示できる:

- **選択肢5（Flight Rising方式・軽量版）**: ページ送りまではせず、新しく増設したラックの行に一時的なハイライト演出（例: 数秒間縁を光らせる、または「NEW」バッジ）を付け、スクロールが必要なことを能動的に知らせる。メリット: 既存の連続スクロールUIを崩さず、低コストで「見えていないものがある」ことを伝えられる。デメリット: 恒常的な対策ではなく、増設した瞬間しか効果がない。
